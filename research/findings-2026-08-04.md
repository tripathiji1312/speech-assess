### 2026-08-04 — Root cause of DDP "marked as ready twice" (subagent 2)

**Subagent question:** What are the documented root causes of "Expected to mark a variable ready only once / marked as ready twice" in PyTorch DDP, specifically gradient checkpointing + LoRA/peft + transformers.Trainer, and the officially documented fixes?

**Answer:** (full report verbatim)

Research complete. All sources fetched live (accessed 2026-08-04). Findings below.

## Numbered findings

**1. The exact error text is generated in PyTorch's DDP reducer — and the message itself documents the root causes.**
Source: `torch/csrc/distributed/c10d/reducer.cpp` in torch v2.10.0 (verified live, https://raw.githubusercontent.com/pytorch/pytorch/v2.10.0/torch/csrc/distributed/c10d/reducer.cpp, function `checkAndRaiseMarkedTwiceError`, lines ~812–863). The message lists:
- Reason 1: "Use of a module parameter outside the `forward` function."
- Reason 2: "Reused parameters in multiple reentrant backward passes. For example, if you use multiple `checkpoint` functions to wrap the same part of your model, it would result in the same set of parameters been used by different reentrant backward passes multiple times, and hence marking a variable ready multiple times. DDP does not support such use cases in default. You can try to use `_set_static_graph()` as a workaround..."
- Reason 3 (appended **only when `find_unused_parameters=True`**, i.e. `has_marked_unused_parameters_` is true — see `REDUCER_CHECK(has_marked_unused_parameters_, ...)` at line 850): "Incorrect unused parameter detection... if an unused parameter becomes part of the autograd graph at a later point in time (e.g., in a reentrant backward when using `checkpoint`), the gradient will show up unexpectedly. If all parameters in the model participate in the backward pass, you can disable unused parameter detection by passing the keyword argument `find_unused_parameters=False`... If unused parameters in the model do not change over iterations, You can try to use `_set_static_graph()`..."
- The "marked as ready twice" line: "Parameter at index ... has been marked as ready twice. This means that multiple autograd engine hooks have fired for this particular parameter during this iteration." (line 822).
- **Important inference for your crash:** your log shows only reasons 1 and 2, *not* reason 3. Per the reducer code, reason 3 is only printed when `find_unused_parameters=True`. Your crash is therefore consistent with `find_unused_parameters=False` and matches reason 2 (reentrant-backward reuse of the same parameter), not the unused-parameter path.

**2. PyTorch DDP API docs — official statement on gradient checkpointing + DDP.**
https://pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html (redirects to https://docs.pytorch.org/docs/2.13/generated/torch.nn.parallel.DistributedDataParallel.html, verified live):
> "DistributedDataParallel currently offers limited support for gradient checkpointing with `torch.utils.checkpoint()`. If the checkpoint is done with `use_reentrant=False` (recommended), DDP will work as expected without any limitations. If, however, the checkpoint is done with `use_reentrant=True` (the default), DDP will work as expected when there are no unused parameters in the model and each layer is checkpointed at most once (**make sure you are not passing `find_unused_parameters=True` to DDP**). We currently do not support the case where a layer is checkpointed multiple times, or when there unused parameters in the checkpointed model."

**3. What `find_unused_parameters` and `static_graph` do (official docs).**
Same DDP API page (verified live):
- `find_unused_parameters` (default `False`): "Traverse the autograd graph from all tensors contained in the return value of the wrapped module's `forward` function. Parameters that don't receive gradients as part of this graph are preemptively marked as being ready to be reduced."
- `static_graph` (default `False`): "When `static_graph` is set to be `True`, DDP will support cases that can not be supported in the past: 1) Reentrant backwards. 2) Activation checkpointing multiple times. 3) Activation checkpointing when model has unused parameters. 4) There are model parameters that are outside of forward function." (This is the constructor arg; `_set_static_graph()` is the equivalent method called after construction.)
- The DDP design note (https://docs.pytorch.org/docs/2.13/notes/ddp.html, verified live) confirms `prepare_for_backward()` "traverses the autograd graph to find unused parameters when `find_unused_parameters` is set to `True`" and that this "introduces extra overheads."

### 2026-08-04 — Unsloth-specific: smart GC patch vs DDP (subagent 3)

**Subagent question:** What are the KNOWN issues and officially recommended fixes from the Unsloth project for multi-GPU (DDP) training combined with gradient checkpointing, and specifically for this "marked as ready twice" error?

**Answer:** (full report verbatim)

All research questions are now answered with primary-source verification. Here is the complete report.

## Answer

**Root cause (verified in source):** Unsloth's `use_gradient_checkpointing="unsloth"` does **not** use `torch.utils.checkpoint`'s reentrant backward. It patches `torch.utils.checkpoint.checkpoint` and `transformers.modeling_utils.checkpoint` with `unsloth_checkpoint`, which **forces `use_reentrant=True`** and routes through a custom `UnslothCheckpointFunction(torch.autograd.Function)`. That function's `backward` re-runs the forward (`ctx.run_function(*detached_inputs)`) and then calls `torch.autograd.backward(outputs_with_grad, args_with_grad)` — reentrant-*style* recomputation. When a LoRA parameter is consumed by more than one such checkpointed segment, DDP's hooks fire more than once → "Expected to mark a variable ready only once … marked as ready twice". The crash line in the user's traceback (line 808) is exactly this `torch.autograd.backward` call in current main.

**Official status (verified via GitHub API):**
1. **Issue #3713** (the exact bug, Qwen2.5VL 7B + DDP) — **CLOSED 2025-12-20** by the merge of **PR #3751** "Fix VLM + DDP checkpointing" (djsaunde, merged 2025-12-20T03:09:16Z). Maintainer confirmed: *"Seems like this is an edge case with DDP + re-entrant gradient checkpointing + VLM models specifically."* The merged fix is **VLM-only**.
2. The merged fix (in `unsloth/models/vision.py:2115-2131`) is: under `is_distributed()`, **unpatch** the smart-GC/offload patch and force native **non-reentrant** checkpointing (`use_reentrant = not is_distributed()`). It does **not** preserve CPU offloading.
3. The improved fix that keeps offloading — **PR #4077** (nepfaff) — was **closed WITHOUT merge on 2026-03-12**; its replacement **PR #4240** (danielhanchen, "Replacement for #4077 due to Studio rebasing") is **still OPEN as of 2026-08-04**. So the offload-preserving DDP fix is **not in any release**.
4. **LLM path has no DDP handling at all**: `is_distributed()` is used in exactly one place in the whole `unsloth` package (`vision.py:2117`); `llama.py` hardcodes `use_reentrant = True` (lines 1184, 3627) with no DDP gating. The user's log showing "Will smartly offload gradients to save VRAM!" + "Double buffering enabled" means the smart patch was active during their backward — consistent with the **LLM path**, where no official fix exists.
5. **Version status**: unsloth_zoo 2026.8.2 was released 2026-08-03 (latest 2026.8.3, 2026-08-04). The VLM fix has been in main since 2025-12-20, so 2026.8.2 contains it; the #4077/#4240 improvements are **not** in 2026.8.2. Whether the user's crash is on the LLM or VLM path is UNVERIFIED (see below).
6. **No documented flag disables smart offload/double buffering.** The docs' own ask-me answer: *"I can't find any environment variable in the docs that disables Unsloth's 'smart gradient offloading' or any 'double buffering' behavior under DDP."* However, the source contains an **undocumented** env var `UNSLOTH_DISABLE_DOUBLE_BUFFER=1` (`unsloth_zoo/gradient_checkpointing.py:82-83`) that forces double buffering off — it does **not** disable the smart offload itself.
7. **Docs DDP guide** contains no gradient-checkpointing guidance and no recommendation to disable GC for multi-GPU.

**Answer (root cause, verified directly from fetched sources):**
1. **Unsloth's patched model forward hardcodes `use_reentrant=True`.** Fetched https://raw.githubusercontent.com/unslothai/unsloth/main/unsloth/models/llama.py — `LlamaModel_fast_forward` contains:

       hidden_states,
       mask,
       attention_mask,
       position_ids,
       use_reentrant = True,      # hardcoded

### 2026-08-04 (third run) — Root cause of 3rd smoke-test failure: captured `_gradient_checkpointing_func` partial (transformers 5.5.0 GradientCheckpointingLayer)

**Subagent question:** N/A (direct investigation triggered by the user's third crash log: same "marked as ready twice" error at `torch/utils/checkpoint.py:325` even with the `torch.utils.checkpoint.checkpoint` module-attribute wrapper active).

**Answer (root cause, fully verified from fetched sources):**

1. **Transformers 5.5.0 Qwen3 is architecturally different from the Llama path unsloth patches.** `Qwen3DecoderLayer` INHERITS from `transformers.modeling_layers.GradientCheckpointingLayer` (verified: https://raw.githubusercontent.com/huggingface/transformers/v5.5.0/src/transformers/modeling_layers.py). `Qwen3Model.forward` does NOT call `torch.utils.checkpoint.checkpoint` — it iterates `self.layers` and calls `decoder_layer(...)` directly; checkpointing happens inside `GradientCheckpointingLayer.__call__`:
   ```python
   def __call__(self, *args, **kwargs):
       if self.gradient_checkpointing and self.training:
           ...
           return self._gradient_checkpointing_func(partial(super().__call__, **kwargs), *args)
       return super().__call__(*args, **kwargs)
   ```
   The call goes through **`self._gradient_checkpointing_func`** — a captured reference on the module instance, NOT a runtime lookup of `torch.utils.checkpoint.checkpoint`. This is why the module-attribute wrapper (mechanism 1 of the previous fix) was bypassed.

2. **How `_gradient_checkpointing_func` gets bound to the REENTRANT checkpoint (full chain, all verified):**
   - unsloth `patch_peft_model` (unsloth/models/llama.py:3624-3627, fetched from main): `model = prepare_model_for_kbit_training(..., use_reentrant = True, ...)` — hardcoded.
   - unsloth's own `prepare_model_for_kbit_training` (saved source tool_fcde389fe0010IBPBCrqJcrw0f:2292-2306): forwards `use_reentrant=True` into `prepare_model_for_training(...)`.
   - transformers 5.5.0 `PreTrainedModel.gradient_checkpointing_enable` (modeling_utils.py:3079-3103, saved full source tool_fce227599001Ecasur3SeRHKSV): `gradient_checkpointing_func = functools.partial(checkpoint, **gradient_checkpointing_kwargs)` (line 3096) — **captured at enable time**; then `self._set_gradient_checkpointing(enable=True, gradient_checkpointing_func=...)` (line 3103).
   - `_set_gradient_checkpointing` (modeling_utils.py:3121-3133): sets `module._gradient_checkpointing_func = gradient_checkpointing_func` on every `GradientCheckpointingLayer` submodule (line 3133).
   - Net effect: every `Qwen3DecoderLayer._gradient_checkpointing_func` is `functools.partial(torch.utils.checkpoint.checkpoint, use_reentrant=True)` → reentrant backward at `torch/utils/checkpoint.py:325` → DDP "marked as ready twice". Matches the 3rd crash log exactly.

3. **Why the previous wrapper-only fix failed:** the wrapper patches the module attribute `torch.utils.checkpoint.checkpoint`; the captured partial holds a direct reference to the ORIGINAL function and never re-resolves the attribute. (Also: with `use_gradient_checkpointing=True`, unsloth unpatchs its smart GC BEFORE `prepare_model_for_kbit_training` runs, so the captured reference is torch's native checkpoint — consistent with the crash being at torch:325, not unsloth_zoo:808.)

4. **The fix (implemented in this run):** `_force_nonreentrant_checkpointing(model)` now does BOTH:
   - Mechanism 1 (kept): wrap `torch.utils.checkpoint.checkpoint` + `transformers.modeling_utils.checkpoint` module attributes to force `use_reentrant=False` (covers any direct call, e.g. unsloth's patched forward for non-GradientCheckpointingLayer models).
   - Mechanism 2 (new): iterate `model.modules()` and overwrite every `_gradient_checkpointing_func` with `functools.partial(original_checkpoint, use_reentrant=False, determinism_check="none")`. `determinism_check="none"` is valid only for `use_reentrant=False` (torch checkpoint.py:465-466) and silences non-reentrant determinism warnings with unsloth's fast kernels.
   - Called after `get_peft_model` (must be AFTER, since peft's enable is what binds the reentrant partial) AND re-applied right before `trainer.train()` as idempotent insurance (plain transformers.Trainer does not re-enable GC — `args.gradient_checkpointing` is not set in train_sft.py's TrainingArguments — but the second call is cheap).
   - Prints `[DDP fix] forced non-reentrant checkpointing on N module(s)` for diagnosis (expect N = 1 + 36 decoder layers = 37 for Qwen3-4B).

**Evidence:** transformers v5.5.0 modeling_layers.py (GradientCheckpointingLayer.__call__); modeling_utils.py:3079-3103, 3096, 3121-3133 (saved full source); unsloth main llama.py:3624-3627 (`prepare_model_for_kbit_training(..., use_reentrant=True)`); unsloth's prepare_model_for_kbit_training wrapper (saved source :2292-2306); peft chain inferred from those + empirical crash location (torch/utils/checkpoint.py:325 = native reentrant `CheckpointFunction.backward`, torch 2.10.0 source); user's 3rd crash log; local mock test (fake torch/transformers modules, real train_sft.py imported) — mechanism 1 PASS, mechanism 2 PASS, idempotency PASS; `python3 -m py_compile` PASS.

**Not verified:**
- Whether the installed unsloth 2026.8.2 wheel's `patch_peft_model` byte-for-byte matches the fetched main (llama.py:3624-3627). The empirical crash (native reentrant at torch:325 with `use_gradient_checkpointing=True`) proves the reentrant-binding chain exists in the installed wheel regardless of exact line numbers.
- Whether `determinism_check="none"` is needed or merely cosmetic on Kaggle (unsloth fast kernels may not trigger the determinism warning; harmless either way).
- VRAM fit of native non-reentrant GC at batch 4/seq 2048 on 2×T4 (14.5 GB) — still must be confirmed by the next 3-step smoke test; fallback `--batch-size 2 --grad-accum 4` documented in KAGGLE_TRAINING.md.
- Whether unsloth's patched Qwen3 forward (if any) also calls `torch.utils.checkpoint.checkpoint` directly — if it does, mechanism 1 covers it; if the layers are GradientCheckpointingLayer instances, mechanism 2 covers it. Both are now in place.

**Contradictions/resolution:** The previous run's fix assumed the checkpoint call went through the `torch.utils.checkpoint.checkpoint` module attribute at call time (based on unsloth llama.py's `LlamaModel_fast_forward` full-path call). The 3rd smoke test disproved that assumption for Qwen3 in transformers 5.5.0: the active path is `GradientCheckpointingLayer.__call__` → captured `_gradient_checkpointing_func`. Resolution: direct source inspection of modeling_layers.py + modeling_utils.py showed the captured-partial mechanism; the fix now targets both paths. Trust empirical crash evidence over source-inferred call paths.

**Other discoveries:** transformers 5.5.0's `gradient_checkpointing_enable` default is `{"use_reentrant": False}` (modeling_utils.py:3094) — so a plain transformers model (no unsloth/peft) would be DDP-safe by default; the reentrant binding comes specifically from unsloth's `use_reentrant=True` in its `prepare_model_for_kbit_training` call. Also: unsloth's vision.py:2152-2165 intercepts `gradient_checkpointing_enable` to force `use_reentrant=True` for Gemma3N — the same interception pattern we now use (in reverse) for DDP.
